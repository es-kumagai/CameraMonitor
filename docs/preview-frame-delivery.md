# カメラ映像の配信と購読寿命

## 症状と原因候補

複数カメラの一覧で映像が止まることがある。報告時点の再現条件は不明であり、今回のコード調査だけで実際に起きた停止の原因を断定しない。

変更前はキャプチャコールバックと各プレビューの両方が、フレームごとに `Task.detached` を生成していた。画像変換やメインアクターの表示が遅れると、保持する `CMSampleBuffer` と実行待ちタスクの数に上限がない。[Apple の TN2445](https://developer.apple.com/library/archive/technotes/tn2445/_index.html) も、バッファの長時間保持でフレームの供給が止まりうると説明している。

また、同一のオブザーバーを使ってカメラ変更ごとの非同期登録・解除を行っていたため、処理が重なると新しい登録を古い処理が解除しうる。`removeFromSuperview()` では解除するものの、同じカメラを再表示した場合の登録再開も保証されていなかった。オブザーバーがビューを `unowned` で参照する寿命の問題もあった。

## 配信の契約

- `VideoCapture` はカメラごとの直列コールバック内で、サンプルバッファを遅延描画なしの独立した `CGImage` に変換する。同じカメラの各プレビューはその画像を共有する。
- キャプチャバッファをタスクや表示キューへ渡さない。画像変換が追いつかないときは `alwaysDiscardsLateVideoFrames` によって古いフレームを破棄する。
- オブザーバー一覧は `Mutex` で保護し、取得したスナップショットへの通知はロックの外で実行する。解除と行き違う通知はありうるため、終了済みの受信側はそれを受け付けない。
- 各プレビューの受信ストリームは最新の表示待ち画像1枚だけを保持する。表示が遅れてもキューは増えず、次の表示時に最新の画像へ追いつく。
- カメラ変更とウィンドウへの取り付け変更で購読を置き換える。新旧の購読は別のオブザーバーを持ち、古いタスクは自分の登録だけを解除する。ビューの取り外し、解放、キャプチャの解放、タスクのキャンセルで待機を終了する。
- UI はメインアクターで更新し、画像の受信待ちの間はビューを強参照しない。表示前にキャンセルと購読の同一性を確認し、古いカメラの画像を適用しない。

既存の AppKit / Xcode 構成を維持する。デバイス障害やセッションの実行時エラーからの自動再接続は、今回の配信滞留・購読競合の修正には含めない。
